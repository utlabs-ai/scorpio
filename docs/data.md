# Where the data lives

Every place Scorpio keeps data, which copy is the truth, who writes it and how a copy that drifts is put right. Places are named by file and function, not by line, so the table survives edits.

**The rule: new data is registered here first.** A change that adds a table, a column, a KV key, an R2 key pattern, a file under `~/.scorpio/` or a browser storage key adds or updates its row here in the same commit: truth or copy, writer, repair.

**Every table, column group and key has one owner domain**: modules are cut by domain. The owner domain is the only one that writes it. Any other domain reads it through the owner's functions, or through a read-only view the owner publishes, and the view's row lists its readers. The one exception is a one-time backfill in `migrate()`, marked `// backfill`. The "Written by" columns list where the code writes today. A writer outside the owner domain is still to be moved behind the owner's functions. Domains in the topic's Durable Object: room, members, presence (socket attachments, `roomFrameDue`, `blockedPush:*`; once moved, it writes its `members` columns through members' functions), messages, tasks, files, handoffs, schedules, quota, snapshot; retention and search own no data; `nonces` belongs to the technical layer (kernel). Domains in the Worker: accounts, sign-in, devices, rooms-index, topic list, file space, billing, quota (`usage_daily`), ops, push, invites, drive, config (operator settings in KV), language (the `lang` cookie). Topic page: page shell, composer, members panel, tasks, push, theme, topic list. The person's computer (§6) is not cut by domain: each file there already has one writer.

Words used below:
- **truth**: the only place the fact lives; if it is lost, it is lost.
- **copy** / **index**: a second place for a fact whose truth is elsewhere, kept so a page or a job does not have to ask the truth. Every copy names its truth and its repair.
- **repair**: what puts a drifted copy right again. "none" is a known gap (last section).

## 1. The short version

| Data | Truth | Copies |
|---|---|---|
| A topic: name, description, public or private, archived, deleted, its members, messages, tasks, files | the topic's Durable Object (`RoomDO`, one per topic) | D1 `rooms`, `room_members` (index for lists and quotas); D1 `account_files`, `file_rooms`, `storage_usage` (file space); D1 `activity_daily`, `usage_daily`, `rooms.active_at` (counters); KV `public:<id>` (signed-out view of a public topic) |

| The bytes of a file | R2 `rooms/<roomId>/files/<sha256>` | the person's Google Drive (only right before an eviction); `~/.scorpio/topics/<topicId>/files/` (what an agent downloaded) |
| An account, its sign-ins, computers, tokens | D1 `users`, `identities`, `devices`, `agent_tokens` | the handle in every member name and in KV sessions; `users.display_name` in DO `members.display_name` |
| A pending email-code sign-in | D1 `email_login_challenges`, `email_login_sends` (sign-in domain) | the browser's opaque `email_login` cookie points to one challenge; Cloudflare Email Service has separate delivery events |

| Invites and given Pro days | D1 `invites`, `invite_ledger`, `trial_batches`, `trial_codes` | — |

| Which agent sits in which terminal pane | `~/.scorpio/state/registry.json` | — (the server never sees panes) |

## 5. R2 (bucket `scorpio-files`, binding `FILES`)

One key pattern here; a deployment may keep its own keys beside it (a website's films, say), registered in its own docs.

`rooms/<roomId>/files/<sha256 of the bytes>` (file-kind.ts `fileKey`), owned by the files domain. The same bytes in one topic are one object; topics never share objects.
- Written by files.ts `storeFile` from the upload route, **before** the DO's `files` row exists.
- One object deleted by: the upload route, through files.ts `unstoreFile`, when the DO refuses the file; the DO's `dropFileRow` (unsent sweep after 10 min, eviction) when no other row of the topic has the same hash.
- All of a topic's objects deleted by files.ts `deleteRoomObjects` from the DO's `purgeRoom`. That is also the only cleanup for an orphan object (a crash between put and the DO row, or a failed delete).

## 9. Known gaps

Remaining gaps in repairing copies:
1. `rooms` / `room_members` against the DOs: retries and an alert, then a daily repair for topics named by recent `room_index` alerts. The repair needs an existing `rooms` row; it cannot discover a topic whose creation never reached D1.
2. `account_files`, `storage_usage`, `file_rooms` against the DOs' `files`: built once, then only moved by events. A failed `fileGone` write leaves the charge up and the R2 object behind.
3. If the DO starts but creating its D1 `rooms` row still fails after retries, the topic exists in the DO without a list index. A new Worker isolate cannot find it through `roomStub`, and the daily repair skips it because there is no row to select.
4. KV `public:<roomId>`: a failed delete (topic went private or was deleted) is not retried; the key has no TTL.
5. `entitlements` / `payments` against Creem: webhook only; nothing re-reads Creem for a missed event.
6. The DO's `plan` cache: hand-made plan changes (scripts, comps) tell no topic; they wait for the 10-minute expiry.
7. Rows a topic purge leaves behind: `push_muted_rooms`, `drive_rooms`, `drive_files.room_id`.
8. Never pruned: `alerts`, `upload_usage`, `usage_daily`, `activity_daily`, `devices`; on the computer `sessions/`, `topics/<topicId>/files/`, `topics/<topicId>/handoffs/` (a fallback the cloud has since overtaken stays until that seat's next handoff from this computer), `spawns/`; the old `handoffs/<topicId>/` of before 2026-10-16, never read again.
9. An interrupted eviction: the room marks the file deleted in `messages.files` and broadcasts it, then deletes its `files` row and adds `gone_files`, then awaits D1 (`fileGone`) and R2 (`deleteObject`) (room/files.ts `evictFiles` → `dropFileRow`; the message mark is room/messages.ts `markFileInMessage`). A failure in the awaits leaves the D1 index and the R2 object behind with no row in the room to find them by, and space.ts stops evicting once usage is under the limit, so nothing retries it. The room's `files` / `gone_files` are the truth of whether a file exists, `messages.files[].deleted` is a copy of it; a repair needs a durable marker of deletions in progress.

Syncs spread over several places:
1. `rooms`: four modules each remember the D1 side of a DO change (room-index.ts for the topic's own actions, retention.ts, billing.ts, room-report.ts); `inRoom` has seven call sites.
2. The storage charge exists three times (DO `files.charged`, D1 `account_files.charged`, D1 `storage_usage.bytes`); the "heir" rule runs once in the DO and once in SQL.
3. `users.display_name` reaches the DO's members from four places; a topic nobody opens keeps the old name.
4. `entitlements` has ten writers with their own SQL.

## 10. Workspace viewer

Workspace files and Git on the computer are the only content truth. The daemon workspace domain reads an immutable per-request selected directory without writing it. A viewer holds only its current complete file or diff and bounded incoming buffers in volatile memory. The RoomDO workspace domain owns ephemeral pending transfers, connection tokens, QoS counters and deadlines; pending content is not persisted. Presence socket attachments retain connection identity, the logical live-group epoch, a SHA-256 token verifier and at most two in-flight request/transfer/deadline markers per viewer. They never hold raw tokens, operation parameters, paths, file names, listings or file bytes. Hibernation recovers identities but fails and clears lost transfer markers; it never replays content. Membership/device records retain their existing owners; workspace reads them through members. No SQL, KV, R2, cache or export stores workspace content. A transfer reset cancels only its old request; a connection reset invalidates that connection’s credentials. Neither replays content.

The panel owns the numeric localStorage preference `workspace-panel-width-v1`. It stores only the last chosen width in CSS pixels; window bounds clamp it on reuse. The only path exception is `view-files-directory-v1:<account>:<computerId>`, one canonical last-successful root path across topics, written by that viewer after complete root list; no ids, history, selection, entries or content. It is cleared for the authenticated account on logout/account deletion. Existing width storage remains numeric only.
